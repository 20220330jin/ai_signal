## 4. 별도 기술 해설 (Karpathy 영상의 직역이나 직접 강의 목차 아님)

### LLM
토큰 예측 모델은 지식을 압축적으로 보유하지만 외부 세계의 상태·파일·DB를 자율 변경할 권한이 없다. 이를 실행 가능하게 하는 것은 별도 시스템이다.

### Agent
모델이 목표, 도구, 관측 결과를 토대로 다음 행동을 결정하는 반복 실행 구조. 도구 사용 권한과 승인 경계가 중요하다.

### Harness
모델 주변에서 컨텍스트 구성, 도구 명세, 실행 경계, 메모리, 관찰·평가를 관리하는 소프트웨어. Prompt와 Harness는 대체 관계가 아니다. 안정적인 실행을 위해 둘 다 필요하다.

### Loop
`goal → act → observe → check → revise/stop`을 반복한다. 종료 조건 없이 무제한 재시도하면 비용 증가·중복 부작용·잘못된 자기확신이 발생한다. 체크는 참/거짓이나 점수로 실패할 수 있어야 하며, 실패 횟수·예산·사람 승인 조건을 둔다.

### Graph
일반적으로 노드(작업/에이전트)와 엣지(입출력/의존성/분기)로 구성된 실행 흐름. 단일 LLM의 사고력 증대 자체가 아니라 병렬성, 작업 의존 관계, 재시도와 상태 전파를 통제하기 위한 구조다. 모든 업무가 다중 에이전트 그래프를 요구하지 않는다.

### 도구 호출 루프(예시)
1. 사용자가 요구를 전달한다.
2. 모델은 도구 호출 형식으로 이름·인자를 출력한다.
3. 하네스가 권한과 인자를 검증하고 외부 실행한다.
4. 결과가 컨텍스트에 다시 들어온다.
5. 모델이 계속할지, 끝낼지 판단한다.

모델이 실제 코드를 직접 실행하는 것이 아니라 호스트가 모델의 요청을 해석해 실행하는 것이라는 차이가 핵심이다.

## 5. Anthropic SIGNAL-007과 비교

| 질문 | SIGNAL-008 기술 프레임워크 | SIGNAL-007 Anthropic 공식 아키텍처 |
|---|---|---|
| 무엇을 만들 것인가 | Agent → Harness → Loop → Graph의 이해 순서(편집 정리) | Brain·Hands·Session 분리(공식 설계) |
| 상태 보존 | Loop와 graph에 durable checkpoint가 필요 | Session의 영구 이벤트 저장 |
| 실행 경계 | Harness의 도구 검증·권한 분리 | 독립된 Hands·sandbox |
| 평가 | 실패할 수 있는 check가 loop의 품질을 결정 | Evals/outcome grading과 연결 가능 |
| 주의 | 강의 직접 인용으로 귀속하지 말 것 | 공식 성능 수치는 공급자 발표로 분류 |

**연결 통찰:** Graph는 작업 *흐름*을 설명하고, Session은 실행의 *기록과 수명*을 설명한다. Harness는 두 구조를 조정한다. 셋은 경쟁 개념이 아니라 다른 설계 축이다.

## 6. 실무 영향과 학습 실습

Java/Spring Boot, Python 또는 Node 백엔드에서 개념을 실습할 수 있다.

최소 구현 단계(제안일 뿐 실행하지 않음):
1. 단일 도구 호출 가능한 Agent를 만든다(처음에는 읽기 전용).
2. Harness에서 입력 검증·권한·타임아웃·token/비용 제한을 중앙화한다.
3. 한 번 실패하는 테스트를 만들고 재시도 2회·초과시 사람에게 보고하게 한다.
4. 작업 노드 3개로 순차 → 병렬 → 조건 분기를 테스트한다.
5. 실행 이벤트 저장·중복 실행 방지·장애 후 재개를 붙인다.
6. 비교 측정: 작업 성공률, 허위 성공, 비용, 재시도, 사용자 승인 누락.

**AI/데이터·백엔드 커리어 관점:** 좋은 프롬프트보다 분산 작업, 신뢰성, 상태 저장, 평가, 보안 경계 설계를 정확히 구현하는 능력이 에이전트 엔지니어링의 차별점이 될 수 있다. 이는 채용 수요에 대한 실측 결론이 아니라 편집 분석이다.

## 7. 반론·한계

- Harness가 아무리 정교해도 모델의 판단 오류를 없애지는 못한다.
- 자동 평가의 루브릭도 잘못됐을 수 있으므로 독립적인 테스트와 인간 감사가 필요하다.
- Graph 구조는 코드 복잡성과 운영 비용을 증가시키므로 작은 작업은 단일 에이전트가 더 적합할 수 있다.
- 최신 모델마다 툴 사용 능력·API 제약이 달라 하네스 변경과 회귀 시험이 필요하다.
- '실패한 check'가 있다고 해서 시스템이 스스로 지능적으로 개선되는 것은 아니다. 수정 정책·데이터·검증자 설계가 필요하다.
