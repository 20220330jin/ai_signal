## 3분 핵심 브리핑 — 무엇이 새로운가?

**[원문 해설]** 카파시의 문제의식은 “LLM이 문서를 잘 검색하느냐”보다 “문서를 읽고 알아낸 연결과 해석이 다음 작업에도 남느냐”에 가깝다. 매번 원문 조각을 검색해 답을 생성하는 것만으로는, 이전에 어렵게 만든 종합적 설명을 지속적으로 보존하지 못할 수 있다.

그가 제안하는 **LLM Wiki**는 원본 자료와 사용자 사이에 AI가 관리하는 Markdown 지식 문서를 둔다. 새 자료를 읽으면 기존 문서와 비교해 관련 항목을 갱신하고, 자료 간 모순과 연결을 기록한다. 사용자는 어떤 자료가 중요한지와 무엇을 판단할지 결정하고, 에이전트는 반복적인 정리·연결·수정 작업을 돕는다.

**한 문장으로:** 검색해서 답하는 시스템을 넘어, **근거를 추적하면서 이해를 누적하는 시스템**을 만들자는 제안이다.

다만 이것은 **모든 RAG보다 우수하다고 입증된 보편적 결론이 아니다.** 지속 갱신을 포함하는 RAG 설계도 가능하며, 자동 위키가 오류를 줄인다는 보장도 없다.

## 원문 상세 해설 — 카파시의 설계

### 문제: 매번 처음부터 종합하면 생기는 비용

**[원문 해설]** 같은 연구 주제를 여러 번 조사한다고 생각해 보자. 오늘은 A 문서와 B 문서를 비교해 중요한 공통점을 발견했다. 다음 주 새로운 C 문서가 들어왔을 때, 시스템이 A·B·C의 관련 부분을 다시 검색하기만 한다면 지난번에 만든 종합 해석이 별도 지식으로 남지 않을 수 있다.

카파시는 이 간극을 메우기 위해 원문을 읽고 기존 위키를 고치는 작업을 별도 과정으로 제시한다. 새 정보가 기존 주장과 충돌하면 문서를 수정하거나 충돌을 명시하고, 주제·인물·개념 페이지 사이의 연결도 보완한다.

### 세 계층: Raw / Wiki / Schema

| 계층 | 하는 일 | 무엇을 지켜야 하나 |
|---|---|---|
| **Raw sources** | 게시물·논문·메모 등 출처 자료 | 원본을 임의로 고치지 않고 출처·시점을 보존 |
| **Wiki** | 여러 원본을 종합한 현재의 지식 | 주장마다 근거와 불확실성을 연결하고 새 증거에 따라 수정 |
| **Schema** | 에이전트가 따를 작업 규칙 | 문서 구조, 인용, 수정, 검토, 기록 규칙을 명시 |

**[기술 학습]** Raw는 *증거*, Wiki는 *현재의 해석*, Schema는 *해석을 갱신하는 절차*라고 생각하면 쉽다. 세 층을 섞으면 “누군가 실제로 말한 것”과 “AI가 그렇게 해석한 것”이 뒤엉키기 쉽다.

### 세 작업: Ingest / Query / Lint

**Ingest(자료 편입)**: 새 자료를 읽고 관련 문서들을 찾아 추가·수정하며, 충돌하는 주장과 변경 이유를 기록한다. 카파시는 한 자료가 여러 위키 페이지에 영향을 줄 수 있다고 설명한다.

**Query(지식 질의)**: 누적된 위키를 바탕으로 질문에 답하고, 가치 있는 새 종합 결과는 위키에 다시 반영할 수 있다. 답변을 저장할 때도 근거와 해석을 구별해야 한다.

**Lint(정합성 점검)**: 끊어진 링크, 근거 없는 단정, 서로 충돌하는 문서, 오래된 설명, 고립된 문서를 점검한다. **Lint를 실행했다고 내용의 진실성이 보장되는 것은 아니다.**

### 탐색과 도구: 왜 Markdown과 Git인가?

**[원문 해설]** 카파시는 `index.md`로 주제별 탐색을, `log.md`로 시간순 변경 이력을 관리하는 접근을 설명한다. 문서가 많아지면 검색 도구를 추가할 수 있다. Obsidian은 사람이 Markdown 문서를 링크·그래프 등으로 탐색하는 화면으로 활용하고, Git은 변경 내역을 관리한다. Web Clipper, Dataview, Marp 등은 선택 도구다.

**[기술 학습]** Markdown은 읽고 수정하기 쉬운 문서 형식, Git은 변경 이력 관리, Obsidian은 문서 탐색 UI다. 이 도구들이 지식의 정확성을 자동 보장하지는 않는다.

### 철학: 사람이 방치하기 쉬운 위키를 AI가 관리한다

**[원문 해설]** 위키는 처음 만들기보다 지속적으로 관리하는 일이 어렵다. 카파시는 AI가 반복적인 정리 업무를 맡으면 지식이 누적될 가능성을 제안한다. 이 구상은 개인 지식 연결을 지향한 Vannevar Bush의 Memex와도 연결된다.

## 기술 학습 ① — RAG와 LLM Wiki는 어떻게 다른가?

**RAG(Retrieval-Augmented Generation)**는 외부 자료를 찾아 모델의 입력에 제공하고, 그 자료를 참고해 답변하도록 하는 설계 방식이다. 보통 문서 수집 → 분할·색인 → 검색 → 관련 자료 제공 → 답변의 흐름을 갖지만, 구현 방식은 다양하다.

예를 들어 “카파시가 에이전트의 장기 작업에 대해 무엇을 말했나?”라고 질문하면 RAG는 관련 게시물 조각을 찾아 답을 구성할 수 있다. 반면 누적형 위키는 **이전에 비교·검증한 결과가 별도 문서로 남아 있고**, 새 게시물에 맞춰 그 문서를 고칠 수 있도록 설계한다.

| 비교 관점 | 기본적인 검색 중심 RAG 예시 | 지속 갱신형 LLM Wiki 예시 |
|---|---|---|
| 중심 작업 | 질문에 맞는 근거 검색·답변 | 새 자료와 기존 지식의 비교·갱신 |
| 종합 해석의 보존 | 별도 저장 설계가 없다면 일회성일 수 있음 | 위키 문서에 남기는 것이 핵심 |
| 새로운 증거가 들어오면 | 검색 대상이 늘어남 | 관련 종합 문서도 갱신 대상 |
| 강점 | 원문에 가까운 자료를 필요할 때 조회 | 누적 맥락·개념 연결을 탐색하기 쉬움 |
| 위험 | 검색 누락·맥락 손실·부정확한 인용 | 잘못된 해석의 누적·전파·갱신 비용 |

**중요한 반론:** 둘은 배타적인 기술이 아니다. 위키의 근거를 찾는 데 RAG를 쓸 수 있고, RAG 시스템에도 메모리·지식 그래프·문서 갱신을 결합할 수 있다. 따라서 “RAG는 구식이고 위키가 대체한다”는 결론은 부정확하다.

## 기술 학습 ② — 새 자료가 들어왔을 때 실제로 무슨 일이 일어날까?

**[오늘AI 적용 · 가상 시나리오]** 기존에 “에이전트의 장기 작업은 오류 누적에 취약하다”라는 주제 설명이 있고, 새로운 실험 보고서가 도착했다고 가정한다. 아래 보고서와 수치는 **가상 예시**이며 실제 연구 결과가 아니다.

### 1단계. 원본은 그대로 남긴다

```text
sources/
  2026-10-example-agent-evaluation.md
posts/
  SIGNAL-002.md
topics/
  ai-agents.md
```

원본에는 출처 URL, 작성자, 발표 시점, 원문 확인 상태를 기록한다. 저작권이나 접근 제한이 있으면 원문 전체를 복제하지 않고 허용 범위의 메타데이터·요약·링크만 남긴다.

### 2단계. 기존 주장과 비교한다

기존 `topics/ai-agents.md`:

```md
# AI 에이전트
장기 작업에서 오류 누적이 중요한 한계다.
근거: SIGNAL-002 (작성자 주장)
```

새 자료는 특정 평가 조건에서 개선을 보고했다고 가정한다. 그렇다고 “이제 장기 작업 문제가 해결됐다”라고 바꾸면 안 된다. 평가 환경·성공 기준·실패 사례가 다른지 확인해야 한다.

### 3단계. 종합 문서를 갱신한다

갱신된 `topics/ai-agents.md`의 예시:

```md
# AI 에이전트

## 현재 이해
일부 평가 조건에서는 장기 작업 성능 개선이 보고된다.
다만 환경과 검증 기준에 따라 성능 차이가 클 수 있다.

## 근거
- SIGNAL-002: Karpathy의 역량 격차 주장
- 2026-10 가상 평가 자료: 별도 재현 필요

## 불확실성
실제 운영 환경의 오류 누적 감소 여부는 미확인.
```

원본을 수정하지 않고 **현재의 해석**을 고치는 것이 핵심이다.

### 4단계. 변경 기록과 검토 상태를 남긴다

```md
# log.md
- 2026-10-21: ai-agents.md 갱신
  - 이유: 새 평가 자료와 기존 주장 비교
  - 근거: SIGNAL-002, 가상 평가 자료
  - 상태: 검토 필요
```

자동 변경이 중요한 결론에 영향을 미친다면 사람이 확인할 때까지 “검토 필요”로 유지한다.

## 기술 학습 ③ — 에이전트에게 어떤 규칙을 줘야 하나?

**[오늘AI 적용]** 다음은 실제 프로젝트에서 활용할 수 있는 간단한 규칙 예시다. 카파시 원문의 규칙을 그대로 옮긴 것은 아니다.

```md
# AGENTS.md — 지식 관리 규칙

1. 원본 기록은 수정하지 않는다.
2. 새 주장에는 출처 링크와 확인 상태를 남긴다.
3. 작성자 주장, 외부 검증, AI 해석을 구분한다.
4. 기존 문서와 충돌하면 삭제보다 차이를 기록한다.
5. 중요한 결론 변경은 사람의 승인을 받는다.
6. 변경한 문서와 이유를 log.md에 기록한다.
7. 근거를 찾지 못한 주장은 사실로 단정하지 않는다.
```

이 규칙은 모델의 실수를 완전히 막지 못한다. 특히 여러 파일을 동시에 바꾸는 경우 **변경 전후 비교(diff)**와 승인 절차가 중요하다.

| **확인되지 않은 자료** | X 게시물 본문은 직접 접근 제한으로 미확인 |

### 오류가 누적될 수 있다

AI가 원문을 잘못 읽고 종합 문서를 수정하면, 나중의 질의는 잘못된 위키를 다시 근거로 사용할 수 있다. 특히 여러 문서에 같은 오해가 복제되면 오류를 찾아내기 어려워진다. **원본 링크, 검증 상태, 변경 이력, 사람의 검토**가 필요한 이유다.

### 유지보수 비용이 증가할 수 있다

자료 하나가 여러 문서에 영향을 주면 검색·읽기·비교·수정·검토가 모두 비용이 된다. 문서 수가 적거나 질문이 단순한 프로젝트에서는 기본 RAG나 단순 색인이 더 적합할 수 있다.

### '정합성'과 '진실성'은 다르다

서로 다른 두 위키 문서가 같은 내용을 말한다고 해서 그 내용이 참이라는 뜻은 아니다. 두 문서가 동일한 잘못된 출처를 반복했을 수도 있다. Lint는 **문서 관리 품질을 돕는 절차**이지 사실 검증을 대체하지 않는다.

### 좋은 비교 실험은 무엇인가?

동일한 자료와 질문을 주고 **검색 중심 방식**과 **갱신형 위키 방식**을 비교한다. 답변 정확성뿐 아니라 출처 추적 가능성, 새 자료 반영 시간, 사람의 수정 횟수, 비용, 오류 전파 여부를 함께 측정해야 한다. 이런 비교 없이 어느 쪽이 우수하다고 단정하면 안 된다.

## 오늘AI에 적용한다면 — 현재와 제안을 구분하자

**현재:** `posts/SIGNAL-NNN.md`에 개별 분석을 저장하고, `topics/`에 주제 문서를 두며, `INDEX.md`와 웹사이트에서 게시물을 탐색한다. 원문 검증 상태를 기록하고 관련 글을 연결하고 있다.

**제안(미구현):** 원본 메타데이터를 별도 관리하고, 주제 문서를 새 글마다 비교·갱신하며, 변경 이력 `log.md`와 정기 Lint 점검을 운영한다. `AGENTS.md`에 출처·충돌·승인 규칙을 명시할 수 있다. 이 단계들은 **이번 SIGNAL-003 글 개편만으로 자동 구현되지 않는다.**

## 이 글의 학습 내용과 원문의 경계

이 문서는 Gist의 내용을 바탕으로 작성한 **한국어 해설 및 교육용 재구성**이지 원문 전체의 문장별 번역이 아니다. 코드·폴더 구조·실습·비교표는 이해를 위한 오늘AI의 예시다. 새로운 독립 검증 자료를 확인하지 않았으므로 일반적인 RAG 대비 우월성이나 특정 수치 성능을 주장하지 않는다.
