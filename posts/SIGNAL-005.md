## 3분 핵심 브리핑

AI 에이전트가 외부 시스템의 변화를 알아차리는 전통적인 방법은 사용자가 다시 요청하거나 시스템이 반복적으로 확인하는 **폴링(polling)**이다. **MCP Events**는 MCP 서버가 지원하는 이벤트 종류를 공개하고, 클라이언트가 관심 있는 사건을 구독한 다음, 사건 발생 시 전달받도록 하는 모델이다. Svix 글은 그중 **ChatGPT의 웹훅(Webhook) 전달 경로**를 구체적으로 설명한다.

핵심은 웹훅을 새로 발명했다는 것이 아니다. **AI 클라이언트가 어떤 이벤트를 어떤 조건으로 구독하고, 어디로 안전하게 전달받을지 표준화된 인터페이스로 협의한다**는 점이다. 예를 들어 문서의 댓글이 생성됐을 때 ChatGPT가 이벤트를 받아 사용자에게 후속 작업을 수행할 수 있다.

다만 이벤트 수신과 AI의 임의 실행은 같은 뜻이 아니다. 인증·사용자 권한·구독 범위·클라이언트 정책이 선행되어야 한다.

## 1. 왜 필요한가: 요청형 도구와 사건형 작업의 차이

일반적인 MCP 도구 호출은 클라이언트가 필요할 때 서버에 요청을 보내고 결과를 받는다. 이는 ‘현재 상태를 알려줘’에 적합하지만, ‘새로운 일이 생기면 알려줘’에는 반복 확인이나 별도 알림 인프라가 필요하다.

이벤트 구독은 이 흐름을 뒤집는다. 클라이언트가 먼저 **관심 사건과 필터**를 등록해 두고, 나중에 외부 시스템이 사건을 감지하면 지정된 경로로 알린다. 따라서 이벤트를 받는 시점과 사용자가 대화하는 시점이 다를 수 있다.

## 2. 작동 방식: 발견 → 구독 → 검증 → 전달

1. **발견 — `events/list`:** MCP 서버가 제공하는 이벤트 이름, 구독 인자 스키마, 페이로드 구조, 지원 전달 방식을 알린다.
2. **구독 — `events/subscribe`:** ChatGPT가 이벤트 이름과 필터, 콜백 URL, 서명 검증용 비밀값을 서버에 보낸다. 서버는 사용자 권한과 입력을 검증한다.
3. **콜백 검증:** 서버는 지정된 콜백이 실제로 수신 가능한지 확인하고, 구독 소유자·만료 시각·필터를 저장한다.
4. **이벤트 발생:** 예컨대 `comment.created` 사건이 발생하면 서버가 해당 구독의 필터를 적용한다.
5. **서명된 전달:** 서버 또는 Svix가 표준 웹훅 헤더와 서명을 포함해 콜백으로 전송한다. 수신자는 서명과 중복 여부를 검증한다.
6. **후속 작업:** ChatGPT 측 정책·권한에 따라 사용자에게 사건을 알리거나 허용된 후속 처리를 진행한다.
7. **갱신·해지:** 구독은 만료 전에 갱신할 수 있고 `events/unsubscribe`로 중단할 수 있다.

**중요:** 이벤트가 도착했다고 무조건 임의의 도구 실행이나 운영 시스템 변경이 허용되는 것은 아니다.

## 3. Svix는 무엇을 제공하는가?

Svix는 이벤트를 전달하는 웹훅 인프라를 제공한다. 원문에 따르면 ChatGPT용으로 두 개의 전용 라우트를 제공한다.

| Svix 경로 | 역할 |
|---|---|
| `POST /app/{app_id}/chatgpt-mcp-events/subscribe` | 구독 엔드포인트 생성 또는 갱신 |
| `POST /app/{app_id}/chatgpt-mcp-events/unsubscribe` | 구독 비활성화 |

MCP 서버는 사용자의 구독 권한을 직접 판단하고 Svix에 필요한 설정을 전달한다. Svix는 콜백 확인, 서명, 재시도, 비밀값 교체 중 유예기간, 구독 만료 같은 **전달 인프라**를 담당한다. Svix 설명에 따르면 전용 라우트는 새 기능이므로 당시 API 참조 문서나 SDK에 아직 반영되지 않았다.

따라서 **Svix가 MCP Events의 필수 구성요소는 아니다.** 자체 웹훅 서버로 구현할 수도 있지만, 전달·재시도·키 관리·보안의 운영 부담을 직접 져야 한다.

## 4. 기존 방식과 비교

| 방식 | 장점 | 제약 |
|---|---|---|
| 수동 MCP 도구 호출 | 요청 시점과 권한이 명확 | 외부 사건을 자동 감지하지 못함 |
| 주기적 폴링 | 구현·디버깅이 비교적 단순 | 불필요한 요청·지연·호출 제한 |
| 일반 웹훅 | 사건 발생 시 빠른 통지 | 서비스별 구독·인증·스키마 구현 필요 |
| MCP Events + 웹훅 | AI 클라이언트와 이벤트 구독·전달 계약을 구조화 | 지원 클라이언트·구독 정책·콜백 운영에 의존 |
| 스트림/폴링 전달 모드 | 클라이언트 환경에 따라 선택 가능 | ChatGPT의 현재 지원 모드와 설계 초안의 전체 범위는 다를 수 있음 |

MCP Events는 웹훅을 대체하는 별도 네트워크 기술이 아니라, **웹훅 등 기존 전달 방식 위에 AI 클라이언트용 이벤트 계약을 올리는 접근**이다.

## 5. 기술적 위험과 설계 조건

**권한:** 구독 요청자가 특정 문서나 조직의 사건을 볼 권한이 있는지 서버가 검사해야 한다. 이벤트 페이로드 자체가 민감할 수 있다.

**콜백 주소:** 임의 URL로 이벤트를 전송하면 서버 측 요청 위조(SSRF, Server-Side Request Forgery)나 데이터 유출 경로가 될 수 있다. 허용 범위와 콜백 검증이 필요하다.

**서명과 비밀값:** 웹훅 수신자는 메시지의 무결성과 출처를 확인해야 한다. 비밀값 회전 중에는 이전 키의 짧은 유효기간을 관리해야 한다.

**중복과 순서:** 재시도가 있는 시스템은 같은 사건을 두 번 이상 전달할 수 있다. `eventId` 기반 멱등 처리와 순서 가정 최소화가 중요하다.

**만료와 장애:** 구독 갱신 실패, 콜백 일시 장애, 수신 측 오류에 대비해야 한다. 단순히 ‘웹훅을 보냈다’는 것만으로 사용자가 작업 결과를 확인했다는 뜻은 아니다.

**비용:** 외부 이벤트가 많으면 메시지 전달·저장·AI 후속 작업 비용이 누적될 수 있다. 사건 필터링, 중복 제거, 실행 승인·예산 상한이 필요하다.

## 6. 어디까지 확인됐고, 무엇은 아직 아닌가?

- **확인:** Svix는 ChatGPT MCP Events의 구독/해지 경로와 웹훅 전달 설계를 설명한다.
- **확인:** OpenAI 개발 문서에는 `events/subscribe`의 요청 구조와 권한·콜백 검증 요구사항이 제시돼 있다.
- **확인:** MCP Events 설계 초안은 폴링·스트림·웹훅의 복수 전달 모델을 설명한다.
- **주의:** 설계 초안에 있는 모든 모드가 ChatGPT에서 구현됐다는 뜻은 아니다. Svix는 ChatGPT가 당시 웹훅 방식을 사용한다고 설명한다.
- **미검증:** 계정별 사용 가능 여부, 실제 전달 성공률·지연시간, Svix와 자체 구현의 총비용, 대규모 이벤트 처리 성능.

## 7. 개발자에게 어떤 의미인가?

첫째, AI 에이전트의 활용이 ‘질문을 받으면 답하는 도구’에서 ‘외부 사건을 계기로 일을 시작하는 작업자’로 넓어질 수 있다. 둘째, 이벤트 전달을 신뢰하려면 **인증, 권한, 멱등성, 관찰 가능성, 실패 복구** 같은 전통적인 백엔드 역량이 더욱 중요해진다. 셋째, 모든 문제에 이벤트 구독이 정답은 아니다. 변경 빈도가 낮거나 보안상 외부 콜백을 허용하기 어려우면 폴링이 더 단순할 수 있다.

### 20분 설계 실습

‘문서에 댓글이 달리면 알림’이라는 상황을 가정해 보자. `comment.created` 이벤트에 `document_id` 필터를 두고, 구독 권한 검증 → 콜백 서명 확인 → 중복 `eventId` 무시 → 알림 전송 → 실패 재시도까지 순서도를 작성한다. 같은 요구를 5분 폴링으로 구현했을 때 요청량과 지연을 비교해 본다. 실제 ChatGPT 계정 연결은 별도 검증 단계다.

## 8. 오늘AI 분석: 진짜 변화는 이벤트 자체가 아니다

**편집 판단:** 기술적으로 새롭다고 평가할 부분은 웹훅이나 이벤트 큐가 아니라, **AI 클라이언트와 외부 서비스가 이벤트 구독 조건·전달 방식·보안 요구사항을 공통 인터페이스로 교환할 수 있다는 점**이다. 성공 여부는 프로토콜 이름보다 권한 분리, 이벤트 신뢰성, 클라이언트 지원 범위에 달려 있다.

이 방향은 AI 에이전트가 오래 실행되는 작업을 수행할 때 특히 의미가 있다. 다만 도입 여부는 ‘사건 발생 즉시 후속 조치가 필요한가’, ‘사용자가 없는 동안 실행해도 안전한가’, ‘실패했을 때 복구할 수 있는가’라는 질문에 따라 달라진다.
