## 핵심 브리핑

이 글은 MCP 도구를 AI가 요청할 때만 사용하는 구조에서 벗어나, 외부 시스템의 이벤트가 AI의 후속 작업을 촉발하는 방식(MCP Events)을 다룬다. 예를 들어 GitHub의 새 PR 또는 데이터 수집 완료 신호를 AI 작업과 연결할 수 있다는 개념이다.

> 주의: 이는 앞선 대화에서 제시된 글의 요지에 대한 **잠정 정리**다. 기능이 현재 모든 ChatGPT 계정에서 정식 제공되는지, 제안·시범 기능인지, MCP 표준에 편입됐는지는 공식 문서와 별도 교차 확인이 필요하다.

## 기술 구조 (개념)

1. 외부 시스템에서 이벤트 발생 (예: GitHub PR 생성).
2. 이벤트 제공자 또는 중계 서버가 구독 대상에게 Webhook 전달.
3. 수신 측이 서명·구독 상태·중복 이벤트를 검증.
4. AI가 허용된 범위의 후속 작업을 수행.

일반적인 MCP 요청/응답과 달리, 이벤트 발생이 처리의 출발점이라는 것이 핵심이다. Webhook은 새로운 발명이라기보다 기존 이벤트 전달 방식을 AI 도구 연결과 결합하는 기술적 패턴이다.

## 원문 관련 기술 주장과 검증 상태

| 주장 | 현재 상태 | 추가 검증 |
|---|---|---|
| MCP Events는 이벤트 기반 AI 작업을 가능하게 한다 | 글의 핵심 취지로 파악됨 · 잠정 | Svix 원문 재열람 |
| `events/list`, `events/subscribe`, `events/unsubscribe` 방식 | 앞선 분석에 등장 · 미확인 | 실제 프로토콜 문서와 정확한 명칭 대조 |
| Webhook 서명 검증, 재시도, 구독 갱신 등이 필요하다 | 일반적인 Webhook 운영 설계로 타당 | Svix 구현 세부 확인 |
| ChatGPT 계정에서 MCP Events를 바로 사용할 수 있다 | **미확인** | OpenAI 공식 문서·실제 계정 기능 확인 |
| Svix가 반드시 필요하다 | **그렇게 단정할 근거 없음** | 대체 Webhook 인프라 비교 |

## AI SIGNAL 프로젝트에 대한 의미

- X API 또는 웹 크롤러가 수집을 끝낸 뒤 `source.collected` 같은 내부 이벤트를 발행하면 후속 분석 파이프라인을 시작하도록 설계할 수 있다.
- **MCP Events 자체는 X 원문 접근 문제를 해결하지 않는다.** X 공식 API와 수집 검증이 별도로 필요하다.
- 비용 대시보드에서는 외부 API 호출 횟수와 수집된 리소스 수를 분리하고, 이벤트 중복 전송이 재과금을 유발하지 않도록 멱등 처리가 필요하다.
- 원문·분석·검증·연결 관계를 분리 저장하고, 출처 유형 `web_article`을 지원한다.

## 개발 프로젝트 적용 가능성 (제안, 미구현)

- **YARDBOUND:** Claude Code 작업 보고/PR 생성 → 변경 내용 검토.
- **HEREWEGO:** 데이터 수집 실패/복구 → 원인 분석 및 운영 보고.
- **곳곳:** 장소 등록 제안·승인 이벤트 → 검증·후속 처리.

위 활용 예는 구현 제안이지 현재 작동하는 기능이라는 뜻은 아니다.
